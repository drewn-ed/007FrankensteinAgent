# Files, desktop connection, schedules and event showcase

Implemented on 9 October 2026 in response to David rejecting the single-form showcase and requesting the missing application capabilities. The approved Wisp visual system is retained. Fieldwork is a fictional target application for the demo, not a new name for the product or an integration with a real event service.

## What now exists

- **Files:** a local file vault, attachments up to 10 MB each / 20 MB per task, text reading up to 120 KB, uploads through observed browser file inputs, generated text artifacts and captured browser downloads. The model receives file IDs, never arbitrary host paths. Uploaded filenames and MIME types are retained. Binary attachments are transferable; their content is not interpreted by the text model. The generated Python sandbox still has no host filesystem access.
- **Desktop:** a trusted Swift/macOS Accessibility bridge, application selection, bounded window/control mapping, click and text entry. Each mutation waits for the operator. The helper is built as `.runtime/Workspace Desktop Bridge.app`; Computer includes a Finder reveal action for adding it to macOS Accessibility. Compilation and signing work. **The development Mac still reports `trusted: false`; actual native clicks/text entry are not verified yet.** No Windows/Linux, screenshots, arbitrary keyboard events, shell, secure fields or system permission/credential apps.
- **Schedules:** durable one-time/15-minute/hourly/daily/weekly schedules with pause/resume and task history. Saved workflows retain their original inputs. The local server must stay running and the Mac awake. Closing the web UI does not stop the scheduler. Busy runs defer execution, missed intervals trigger one occurrence, and dispatch errors pause a schedule. Browser/native schedules must find the same already-connected target and keep normal interaction approval. No OS daemon or wake-from-sleep service is installed.
- **Operator review:** a browser/native task without an independent outcome adapter can be confirmed by the user after checking the application. The event records `operator_confirmation`, not an automated verification. Failed skill tests cannot be overridden through this path.
- **Showcase:** a multi-view event operations app with roster import, preference/capacity allocation, a reserve room, room closure, plan preview, change history, waitlist and downloadable operations reports. The app rejects duplicate seats, lost attendees, unknown IDs, invalid preferences and capacity overflow.

### Failures retained

Five earlier Gemini attempts did not complete. They exposed ambiguous application field contracts, malformed JSON, a transport-schema experiment that returned an unusable action, a test with an unstated capacity, and finally repeated planning plus HTTP 429. Their run IDs and failure reasons are retained in the summary. The Gemini quota run did create two tested skills and import the roster; it did **not** complete the allocation/export and is not counted as success.

Changes prompted by these failures:

- Builder and independent test author receive the same application format and documented field names. The builder can see tests written before implementation.
- Allocation capabilities must accept current participants/rooms/workshops; the showcase admission check refuses a CSV-plus-allocation monolith or hardcoded room conditions. This is a team-written policy, not agent-created discovery.
- Gemini uses structured response schemas for code and test envelopes. Planning remains JSON mode because a partial action schema suppressed required dynamic fields. One format retry remains bounded by the original run budget; quota errors do not retry automatically.
- Exact repeated pure computations reuse their result once; another identical request stops the run instead of continuing to consume model calls.
- A generated artifact can use the exact previous skill output or one named field, and may upload it through the same fixed connector.

The verification workspace was explicitly switched to the authorized ChatGPT provider after the Gemini quota failure. This is not a hidden runtime fallback. Main provider selection remains controlled by Settings. The local execution limit is now 20 model calls / 600 seconds, enforced in code and shown in Settings, to accommodate the complete scenario.

## Remaining competition gap

**Agent-created discovery/management is still not demonstrated.** The catalog protocol and registry infrastructure are hand-written. The successful third task establishes composition of two earlier skills in a clean conversation without rebuilding them, but does not by itself complete the full Frankenstein checklist. No claim that all track requirements are met.

Other limits: one browser origin at a time, HTTP redirects and WebSockets blocked, fresh isolated Chrome session on reconnect, no teammate sharing, no external MCP integrations, no automatic wake/restart of the local server. No claim of validated demand or superiority to competitors.

Transport references checked during this work: [Gemini structured outputs](https://ai.google.dev/gemini-api/docs/generate-content/structured-output?hl=en), [official ChatGPT plan inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference). These document supported transport; they do not prove this application's task correctness.
